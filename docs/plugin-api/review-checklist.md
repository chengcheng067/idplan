# 提交前自检 / 我们审什么

**路径**：fork → 在 `src/plugins/<your-plugin-id>/` 下加四个文件（manifest.tsx / 面板组件 / 纯函数 / spec）→ 在 `PluginRegistryProvider.tsx:46-50` 的清单加一行 → 开 PR。

**我们审什么（按顺序，缺一条即打回）**：

1. **只读性**（CI 静态扫描自动先跑一遍）：不得 import `useRepos` / `core/repositories/*` / `backup.service` / `agent-takeover` / `payload.apply`；`capabilities` 只能出现 `data.read`；`source: 'member'` 时 `defaultEnabled` 必须是 `false`（`third-party-plugin-readonly.spec.ts:61-117`，**四条都是机器判，人只处理它放行的**）。
2. **样式 token**：无硬编码色值（PR 描述里贴亮/暗两主题截图）；无全局 CSS 副作用。
3. **无全局副作用**：模块顶层只有常量与组件定义；无 `window.xxx =` / 无定时器 / 无自启动请求。
4. **单测**：至少一条纯函数 spec（真断言，不许「恒真」）；manifest 的 `id` 未被别人用过（grep `id:` 一行就知道）。
5. **说明自洽**：`summary` 说人话；如果贡献 nav 是 `group:'main'`，PR 描述里注明「已知入口暂不渲染」（§1.4.2），免得验收时大家以为是 bug。

**合并即分发**：进了 `main` 的插件随下一个版本到所有用户手里，默认停用，用户在「设置 → 插件」里自己开。这就是我们要的「谁都能参与、谁都能装」——**代码进我们仓库前有人审，是我们和「随便下载个 exe 双击」之间的全部区别**。

# 第二部分 · 安装分级路线（本报告最重要的判断题）

## 2.1 三级总表

## 2.2 L1：规范公开 + PR 通道（建议先做）

- **用户得到**：GitHub 上一份像样的规范（本文档第一部分）、一个能抄的样板（`weekly-report` 已经是「member 自装」形态：随包、默认关、只读、视觉分层）、一个 PR 模板。
- **我们付的**：主要是写文档；评审由机器扫描（`third-party-plugin-readonly.spec.ts`）+ 五条人审清单承担。
- **诚实的一句**：L1 不满足她「谁去下载安装都无所谓」里的「下载」二字——装的动作仍是「升级版本」。但它满足「开放以及共创」的实质：接口有了、规范公开了、谁都能写、写了能被合并、合并了所有用户都能装（默认关、用户自己开）。**这正是 SketchUp 扩展仓库的白名单模式**：EW 里的扩展也是审查后上架，不是「用户随便装」。
- **顺带收益（这是排序的真正理由）**：前十个外部 PR 会踩出 L2 工具链的真实需求（他们会在什么环境编译、会不会忘记 external react、最想要什么出口）。**先有 PR 再定 L2 的产物格式，比凭空定好。**

## 2.3 L2：本地文件安装（现在不做，讲清技术方案等她拍）

她说的「从文件安装」，在 Electron + Vite + TS 栈上的真实形态。先摆三个**已核实的环境事实**：

1. **生产环境不走 `file://`**：Electron 注册了 `app://` 特权协议（standard/secure/corsEnabled/stream，`electron/main.cjs:249-260`），协议处理器**只服务 `build-dist` 目录**、带防目录穿越、未命中回退 SPA（`electron/main.cjs:264-292`），生产页面从 `app://-/index.html` 加载（`electron/main.cjs:363`）。**用户磁盘上任意路径的 JS，宿主的协议取不到。**
2. **渲染进程是硬化的**：`contextIsolation: true` / `nodeIntegration: false` / `sandbox: true`（`electron/main.cjs:337-344`）⇒ 加载的插件代码碰不到 Node API，但**碰得到整个页面的 JS 世界**：全量 zustand store（Dexie 全库数据）、DOM、`fetch`（全仓零 CSP）。
3. **`window.idplan` 是原生桥不是数据桥**：只有窗口/更新/agent 入口文件三组具名能力（`preload.cjs:19-67`），插件没有正当理由碰它；但它**技术上碰得到**。

### 2.3.1 三条候选路线对比

| | A. 运行时 `import()` 磁盘文件 | B. `sandbox` iframe 跑预编译 IIFE | C. `plugins/` 目录 + 重启识别（安装通道，可叠加 A 或 B） |
|---|---|---|---|
| **做法** | 扩展 `app://` 协议根到 `userData/plugins/`，宿主 `import(/* @vite-ignore */ fileUrl)` 一个 ESM | 安装 = 复制文件到 `userData/plugins/<id>/`；启用 = `<iframe sandbox="allow-scripts">` + `srcdoc` 注入产物，宿主经 postMessage 喂数据与 token | 安装 = 选文件 → 落盘 → 重启 → 启动扫描 manifest 登记进注册表；加载复用 A 或 B |
| **技术上可行吗** | 部分可行：`@vite-ignore` 的 import 保留为运行时导入（Vite 的职责到此为止），但 ① 原生 `file://` 模块在 Chromium 里是 opaque origin，动态 import 被 CORS 挡；要靠扩展协议根变通 ② **插件产物里的 `react`/`react-dom` 从哪来**：必须 external + 宿主在全局喂 React 实例，否则整份 React 打进每个插件包；③ **Vite 不管运行期**——现场编译 TSX 不可能，作者必须用我们提供的预编译工具链出产物 | ✅ 完全可行且标准：sandbox 文档是 opaque origin，读不到宿主 DOM/storage/`window.idplan`/Dexie 内存；主题靠 postMessage 喂 token 值；插件页面 = iframe 全屏覆盖宿主内容区（最简形态，别做「跨 iframe 复用 React 树」——那是月级工程） | ✅ 最薄的一层：安装动作有了明确落点（可罗列、可卸载、可迁移），比「运行时 import 任意路径」可控得多 |
| **能力限制是真的吗** | ❌ **不是**。「只能 data.read」在产物裁剪之外无法强制——作者可以在 IIFE 里手写 fetch/`localStorage`，宿主管不着。是君子协定 | ⚠️ **一半真**：宿主数据面（Dexie/DOM/storage/window.idplan）**结构性地**拿不到；但**网络出口挡不住**（sandbox 不管 fetch 外网），要挡必须先补 CSP（`connect-src`）——全仓现在零 CSP（10-04 审计 W10） | 同所选加载路线 |
| **代价** | 中（协议扩展 + 工具链），但买到的安全是假的 | 中（postMessage 契约 + 沙箱边界 + 一条 iframe CSS 注入链），买到的安全是真的（数据面） | 低-中 |
| **对第三方作者** | 最友好（就是普通 React 组件），但产物格式必须我们定 | 不友好但可接受：插件要按「收快照 → postMessage → 自己渲染」的形状写 | 无感（他们只感觉「装完重开了一次」） |

### 2.3.2 L2 的一句话结论

**正确形态 = C（安装）+ B（加载）：「从文件安装」= 选文件 → 落盘 `userData/plugins/<id>/` → 重启后设置里出现（默认关）→ 启用即在 `sandbox` iframe 里跑 prebundled IIFE。** 路线 A 作为「作者强烈要求与宿主组件同进程渲染」时的后续选项单独议，且必须同时补 CSP。**L2 上线前置：F6（CSP，至少给插件 iframe 一条严格策略）**。

### 2.3.3 「加载前告知」怎么做（她问 SketchUp 就对了）

L2 的信任根与 10-04 设计师的判断一致：**信任根是「用户手上有这个文件」，不是「某服务器说有」**（`plugin-arch-decision-2026-10-04.md` 设计师节）。所以「让你看见你要跑的代码」在 L2 是**真能兑现**的——manifest 与 JS 都在用户手里，安装面板可折叠展示源码摘要、能力清单（v1 只有 `data.read`，清单短到不会像免责书）。

**告知三档（等她拍，见决策点②）**：轻 = 勾选「我信任这个来源」装完默认关；中 = 每次启用前展示 manifest + 能力清单 + 「这是运行在你电脑上的代码」；重 = 展示完整源码。我的建议：**中档**——v1 能力就一条，展示成本低，「每次启用确认」恰好把「装」和「开」钉成两件事（样板已经在做的语义，`weekly-report/manifest.tsx:18`）。

### 2.3.4 如果 L2 现在就要，退而求什么的降级路径

1. **最小可跑版**：不做沙箱，只做 C（安装通道）+ 路线 A 加载，告知做到重档（展示源码）+ 能力声明诚实写「本机制不限制代码行为，信任即授权」。先把「下载安装」的体验立起来，沙箱二期补。
2. **更保守版**：「本地安装」= 把文件放进 `userData/plugins/`，宿主下次启动识别，**同 L1 的编译期打包**（用户自己跑一次 `npm run plugins:build`——不，这条对她不成立，她是设计师）。⇒ 推 1，不推 2。
3. **明确不做**：从 URL / npm 装（设计师 10-04 已否：「不做 URL 安装」；供应链攻击面一步登天）。

## 2.4 L3：远程市场（v2 以后，一句话）

需要签名体系（仓库现在一行签名校验代码都没有，10-04 审计原话：「签名证明谁做的，不证明能做什么」）+ 索引与下载服务 + 版本管理与回退 + 评价/信誉 + 运营。**在 L2 跑稳、F8/F9/D14/D15 全部落地之前，任何一步都是给攻击者发邀请函。** 本报告不展开。

# 第三部分 ·「SketchUp Ruby 控制台」对她的实际含义

她的类比是「比如像 SketchUp 那样，它有 Ruby 控制台」。这个类比**真实但边界要讲清**：

1. **控制台的真实语义**：用户在**自己的机器上**、**主动地**、一段一段运行**自己写的或自己找来的**脚本。SketchUp 的信任根 = 「这台机器上的 Ruby 就是给我用的」。它和「从网上下个扩展自动获得系统权限」是**两件事**——后者（Extension Warehouse 装扩展）同样是安装前授权、可卸载、只碰 SketchUp 数据。
2. 她的句子其实把两件事都说了：「Ruby 控制台」（接口形态）+「让所有人都能参与」（分发）。我们要给的是**规范 + 安装方式**，不是控制台。
3. **我的判断：不做控制台型接口。** 三条理由：① **唯一的重度用户会是她自己**，而她说「我不是很懂完整的开发流程」——做了她也不会用，这是虚无功能，直接踩中她的审美口诀「这东西是在做设计，还是在堆效果？」；② 控制台的收益面只有「调试自己」，而插件作者有更直接的工具（浏览器 devtools 看注册表、vitest 跑单测）；③ SketchUp 需要控制台是因为它当年没有更好的脚本分发方式，我们有 GitHub PR 通道（L1），比控制台开放得更彻底。
4. **保留一句给将来**：若将来真要做，正确形态是「仅管理员可见、逐行即时执行、无网络、不落盘」的受限 REPL，且必须排在 L2 沙箱之后。写进 v2 展望，不进 v1。
